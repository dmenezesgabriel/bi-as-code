# SL-068 — A merged fix or feature becomes a release PR, and merging it publishes `biac` to npm with provenance

## Outcome

The maintainer merges a `fix:` or `feat:` pull request, finds a release pull request that bumps the version and writes the changelog, merges it, approves one environment prompt, and `npm i -D biac` then gives a reader the published version with a provenance attestation.

## Demo

Preconditions are the owner-only acts in "Owner-only acts" below; a session cannot do them.

1. Merge a pull request titled `fix: <something small>` into `master`. Within a few minutes `gh pr list --state open --json title,number,headRefName` lists one release-please PR whose title names `0.1.1`.
2. `gh pr checks <number>` shows the required checks (`gate`, `e2e-browser (1/4)` … `(4/4)`, `storybook`, `commit-messages`, `pull-request-title`, the scanners) running on the release PR: they run only because the PR was opened with a GitHub App token, not `GITHUB_TOKEN`.
3. Merge the release PR. `git ls-remote --tags origin v0.1.1` lists the tag and `gh release view v0.1.1` shows the notes.
4. The `publish` job waits on the `npm` environment. Approve it in the Actions UI.
5. `npm view biac@0.1.1 version` prints `0.1.1`, and in an empty directory `npm i biac@0.1.1 && npm audit signatures` reports a verified attestation for `biac`.
6. In another empty directory `npm i -D biac && npx biac build` exits 0 against the project made by `docs/pages/getting-started.md`, and the page reads the same commands the reader just ran.

## Deviations

| Not ported                                                                               | Why                                                                                                                                   |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Auto-merge of the release PR (owner repos)                                               | This repository is private on the free plan, and the manual merge is the review step before the environment approval                  |
| A separate tag workflow (owner repos)                                                    | release-please creates the tag and the GitHub Release itself; the tag-push chain would need a second App-token hop                    |
| Disabling install scripts before publishing (vite)                                       | `pnpm-workspace.yaml` already blocks them and `npm publish` runs only the package's own `prepack`                                     |
| Publishing a package whose repository is private                                         | Provenance needs a public repository; the first publish runs after the owner makes it public                                          |
| App-credentials preflight that warns and skips (`claude-acc-manager`)                    | Only one repository does it; no upstream documentation or reference repo does                                                         |
| Tag, manifest and `main`-ancestry guard before publishing (`claude-acc-manager`)         | Only one repository does it; release-please and npm document no such step                                                             |
| A post-publish `npm audit signatures` job step and a manifest-equals-`package.json` test | Nothing in the references does either; the demo's step 5 runs `npm audit signatures` by hand, the command npm documents for consumers |
