# Query files, translations, search — 4 reference repositories and our gaps

**Ephemeral.** Construction scaffolding for Phase 5: SQL kept in its own file, translated page content, a search input that filters widgets, and search across pages. Deleted when Phase 5 closes. Nothing here belongs in a durable document — see [ADR-0001](../adr/0001-record-architecture-decisions.md).

## How it was built

One pass over `research_repos/` on 2026-10-17, targeted reads, every path checked with `test -e`. Our side read in `src/` the same day. Fetched that day: https://docs.evidence.dev/features/sql-files, https://docs.evidence.dev/features/translations, https://observablehq.github.io/framework/inputs/search, https://www.i18next.com/translation-function/nesting, https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html; `npm view minisearch` for the package facts.

## Decisions the slices must make

| Id  | Decision                             | Options seen                                                                                                                                                                                                                                                         |
| --- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | How a page names a query file        | evidence path syntax (`data="/queries/x"`) vs a name in our existing named-query scope: `src/web/src/features/pages/interpolate.ts` `interpolateQuery` already expands `{{orders}}` from a `queries` map, so a file query can join that map under a name             |
| D2  | Where query files live               | `queries/` at the project root (evidence) vs beside the page; a build must include only files a page references, as data loaders do (`docs/research/data-loaders.md` D4)                                                                                             |
| D3  | Parameters inside a query file       | Not supported (evidence) vs `{{params.x}}` as in fences. Ours binds params as `?` placeholders (`interpolateQuery` returns `{sql, params}`), so allowing them carries no injection risk                                                                              |
| D4  | Translation values inside SQL        | evidence string-substitutes and needs a `.sql` escaping accessor; ours can bind the value as a `?` parameter, the same path as `{{params.x}}` — no escaping rule for authors to remember                                                                             |
| D5  | Language selection in a static build | evidence resolves per request on the server (`?lang=`, then cookie). `biac build` has no server ([ADR-0008](../adr/0008-static-build-is-a-spa-folder.md)): resolve in the client from `?lang=` + stored choice, or emit one build per language                       |
| D6  | Page language and locale             | WCAG 2.2 SC 3.1.1 (Level A): "The default human language of each web page can be programmatically determined" — `src/web/index.html` hard-codes `lang="en"`; `src/web/src/features/widgets/value/format.ts` hard-codes `LOCALE = "en-US"` for every number and date  |
| D7  | Search-input match semantics         | Per-term prefix, AND across all columns (framework) vs one column with `contains`/`prefix`/`suffix`/`regexp` (mosaic). Ours already has `clauseMatch` with `contains`/`prefix`/`suffix`/`regexp` (`src/web/src/features/crossfilter/clause.ts`)                      |
| D8  | Site-search engine                   | MiniSearch (framework; `minisearch@7.2.0`, MIT, 826,513 bytes unpacked, last modified 2025-09-16 per `npm view minisearch`) vs a hand-written index. A new dependency passes `minimumReleaseAge`/`trustPolicy` and sits behind a wrapper (`.dependency-cruiser.cjs`) |
| D9  | What site search indexes             | Static text only, never query results (framework). Our widgets render data client-side, so the index is built from compiled MDX text, headings and front-matter `keywords`                                                                                           |
