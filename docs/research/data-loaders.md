# Data loaders — 4 reference repositories and our gaps

**Ephemeral.** This is construction scaffolding for Phase 3: which reference repos generate data files from programs, the files to open, and what our `data/` pipeline lacks. It is deleted when Phase 3 closes. Nothing here belongs in a durable document — see [ADR-0001](../adr/0001-record-architecture-decisions.md).

## How it was built

One pass over `research_repos/` on 2026-10-17: targeted reads of the files listed below, every path checked with `test -e`. One probe of `bin/biac dev` with `curl` (commands inline). External claims are cited with the URL fetched that day. `https://observablehq.com/framework/data-loaders` answered `429`, so the Framework claims cite the same page's source on GitHub.

## Who else implements this

| Repo        | Has it                           | Form                                                                                                                                                                                                                                                                                                                                                               |
| ----------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `framework` | **yes**                          | A file `quakes.csv.js` beside the data generates `quakes.csv`: the interpreter is picked by the second extension, the program's stdout is the file, the result is cached under `.observablehq/cache`. Runs on request in preview and for referenced files at build. `sql:` front-matter sources resolve through the same lookup, so a generated file is queryable. |
| `evidence`  | no — hosted SQL models instead   | "Models" are SQL queries that evidence.studio materializes in the background and refreshes every 12 hours (paid plans, beta); the local CLI only lists their status. No local program produces a data file. Source: https://docs.evidence.dev/core-concepts/models (fetched 2026-10-17: "refresh every 12 hours").                                                 |
| `mosaic`    | no                               | `duckdb-server` answers `arrow`/`exec` query messages (`QueryParams` in `pkg/server.py`) over a live DuckDB connection; it neither generates nor caches files.                                                                                                                                                                                                     |
| `streamlit` | no — in-process memoization only | `@st.cache_data` memoizes a function's return value by hashed arguments, with `ttl`, `max_entries` and `persist="disk"`. Relevant only as the reference for cache keys and expiry. Source: https://docs.streamlit.io/develop/api-reference/caching-and-state/st.cache_data (fetched 2026-10-17).                                                                   |

Only 1 of 4 has the feature, and the one that does is the closest product to ours: markdown pages plus client-side DuckDB plus `sql:` front-matter. The capability is justified by the Phase 3 goal (data that is not a static file in the repo: a remote API, a database snapshot, a script's output) and by `framework/docs/sql.md:8`, which routes "a SQL query on a remote database" to a data loader.

## Decisions the slices must make

Where the references disagree, or where Framework's choice has a known cost, the slice that meets it decides and records an ADR.

| Id  | Decision                        | Options seen                                                                                                                                                              |
| --- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Loader model                    | Program writes stdout to a file (framework) vs SQL materialized by a hosted service on a schedule (evidence). Only the first runs locally and fits a static `biac build`. |
| D2  | When a loader runs in dev       | On the first request for its output (framework) vs eagerly at server start                                                                                                |
| D3  | Freshness key                   | Loader mtime only — a loader's own inputs are not tracked (framework) vs a hash of inputs plus `ttl` (streamlit `cache_data`)                                             |
| D4  | Which loaders `biac build` runs | Only outputs referenced by a page's `sql:` (framework) vs every loader under `data/` — our build copies the whole `data/` tree today                                      |
| D5  | Stale cache at build            | Reuse any cached output regardless of mtime (framework, for CI caches) vs re-run when stale                                                                               |
| D6  | Cache location                  | Inside the source root (`.observablehq/cache`, framework) vs a project-root directory; either must be gitignored and kept out of `build/`                                 |
| D7  | Loader failure surface          | Server log + HTTP 500 + whole build fails (framework); ours must also decide what the page shows (a located error, as compile errors are)                                 |
| D8  | Interpreters                    | 12 defaults plus a config map (framework) vs `.js` only to start                                                                                                          |
