# SL-028 — Opening the editor or a page never full-reloads `biac dev`

Milestone: Phase 1 · Known debt · State: open · Depends on: — · Closes: Known-debt "lazy `import()` vite dep cache" row (no `GAP-NNN`)

## Outcome

In `biac dev`, the first `?edit` open and the first visit to any page render in place. Vite never logs `optimized dependencies changed. reloading`, and the page never loses its client state (DuckDB tables, query results, the editor buffer), whatever state `src/web/node_modules/.vite` is in when the server starts.

## Demo

1. `pnpm build:cli`, then `bin/biac dev`. The first start after the change logs `Re-optimizing dependencies because vite config has changed` once, since `optimizeDeps.include` is part of vite's config hash. Every later start logs nothing about re-optimizing.
2. Open `http://localhost:5175/weekly-review?region=West`. In devtools run `window.__probe = 1`.
3. Click `Edit`. The editor opens beside the page, the Region filter still reads `West`, and `window.__probe` is still `1` (no reload). The `bin/biac dev` terminal shows no `dependencies optimized:` line and no `optimized dependencies changed. reloading`.
4. Stop the server, restart it with the `?edit=true` tab still open. The tab reconnects into the editor with no `Failed to fetch dynamically imported module` in the console and no reload line in the terminal.
5. Add `import "@codemirror/autocomplete";` (or any editor package not in the list) to `src/web/src/features/editor/code-editor.tsx` and run the guard test by name (`pnpm -s vitest run <guard file>`). It fails and names the missing specifier. Revert.
6. Run `bin/biac build`, then `grep -rl codemirror dist/web`. It prints nothing, so the editor stays out of the bundle ([ADR-0010](../adr/0010-page-authoring-is-dev-server-only.md)).

Runtime discovery is deterministic: 5 of 5 stale runs and 0 of 1 cold runs. The reload is timing-dependent: 1 of 5 here, plus the 2026-10-10 sighting in the Known-debt row. Vite reloads only when the re-optimize changes the main hash or an already-served dep's `fileHash`, and its guide says it will "reload the page if needed" (https://vite.dev/guide/dep-pre-bundling, fetched 2026-10-13). So the test asserts **no runtime discovery**, not "no reload". Page modules (`virtual:biac-page/*`) caused no runtime discovery on the cold run: the scanner already reaches `echarts`, `shiki` and `@duckdb/duckdb-wasm`, which were all in the cold metadata. The editor edge is the only lazy edge that matters.

The cache goes stale in practice through any source change that makes an already-installed package newly reachable through the lazy edge. The cache key is the lockfile plus the config (`getLockfileHash`, `getConfigHash`), and neither changes. A cached `_metadata.json` with a matching hash is trusted as is: `loadCachedDepOptimizationMetadata` returns it before `addManuallyIncludedOptimizeDeps` runs. So `include` protects only because changing it changes the hash.

## Who else implements this

The feature here is "a dependency reached only through a lazy edge is pre-bundled before the browser asks for it". It's a dev-server concern, so only the repos whose dev server is vite can have it.

Mosaic and streamlit never serve dev to end users. This isn't an invention: it's the defect evidence's config comment describes, fixed the way evidence fixes it.

## Trade-offs and what we adopt

| Axis                           | Options seen (repo → approach)                                                                                                                        | Trade-off                                                                                                                                                                                                                                                                                                       | Our choice, and why                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| How the lazy deps are named    | evidence → hand-kept `optimizeDeps.include`; vite → `optimizeDeps.entries` (crawl the lazy module as an extra entry); framework → no global optimizer | `include` is in the config hash, so any edit to it re-optimizes once and then the deps are bundled at every start. A hand list rots when someone adds a codemirror package. `entries` replaces default inference (it has to re-list `index.html`), and it still depends on the crawl reaching every bare import | **`optimizeDeps.include`** in `src/web/vite.config.ts`, listing the runtime (non-`import type`) bare specifiers the editor imports: today `codemirror`, `@codemirror/view`, `@codemirror/state`, `@codemirror/lang-markdown`, `@codemirror/lang-sql`, `@codemirror/lang-html`, `@codemirror/theme-one-dark`. It's evidence's mechanism, and it's in the config hash, so the list can't be silently ignored. `entries` was rejected because it re-states `index.html` and still trusts the crawl |
| Keeping the list honest        | evidence → none (comment only)                                                                                                                        | An unguarded list rots silently: the next lazily reached package brings the reload back                                                                                                                                                                                                                         | A unit test reads every bare import under `src/web/src/features/editor/` (and any other lazy root) and asserts each is covered by `include`; it fails naming the missing specifier                                                                                                                                                                                                                                                                                                              |
| Shared cache with test servers | — (no reference runs dev servers from tests against the app's cache dir)                                                                              | `test/lib/pages-vite-server.ts` `makePagesServer` uses `configFile: false` (different plugin list → different config hash) on the same `src/web` root, so it re-optimizes into the cache `biac dev` reads                                                                                                       | Out of scope: tracked as a new Known-debt row. ## Deviations

- Evidence's list has no guard. Ours gets a unit test that derives the required set from source, so the list can't fall behind the imports.

## Open decisions

- **Where the guard lives.** No vitest project covers `src/web/*.test.ts` today: `unit` takes `src/**/*.unit.test.ts` but excludes `src/web/**`, `web-unit` takes only `src/web/src/**`, `integration` takes `test/integration/**` and `src/web/src/**/*.integration.test.ts` (`vitest.config.ts`). The guard reads files and needs no DOM, so either it sits under `src/web/src/` (in `web-unit`, jsdom unused) or it sits beside the T2 test in `test/integration/`. Pick one; don't add a vitest project for a single file.
- **Where the guard reads the list from.** The test can import `src/web/vite.config.ts` (it's a plain `defineConfig` object), or the config can import a named constant from a small module beside it. Settle this by checking that `vitest.config.ts`'s `web-unit` project can import the vite config without dragging in `@tailwindcss/vite` side effects, and that `.dependency-cruiser.cjs` allows the edge.
- **Storybook.** `src/web/.storybook` builds on the same vite config, so `include` applies there as well. Confirm `pnpm storybook` still starts on 6175 and the story sweep (`test/e2e-browser/storybook-stories.spec.ts`) stays clean.
