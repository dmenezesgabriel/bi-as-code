# SL-030 — Abandoning a query never touches a closed DuckDB connection

Milestone: Phase 1 — Known debt · State: partial · Depends on: — · Closes: the Known-debt duckdb-wasm worker `null function` / `No prepared statement found with ID` row

> A PRD exists so the executing agent **never guesses and never assumes**. Every path below was checked on disk on 2026-10-13; every number carries the command or script that produced it.

## Outcome

A user who leaves a page, or whose filter change supersedes a query, while DuckDB is still answering no longer makes the duckdb-wasm worker read freed memory: the worker console stays empty and no request is ever posted for a connection that was already disconnected.

## Demo

A numbered script a human runs from a cold start. The slice is not `shipped` until this has been run in the real app.

1. `pnpm build:cli && bin/biac dev --port 5391`, open `http://localhost:5391/crossfilter-scale` in Chrome with DevTools → Console open (level "Verbose", all contexts — the lines come from the worker at level `log`).
2. Drag the Distance slider's `Maximum` thumb left and release; **immediately** click `Weekly review` in the sidebar; then browser Back. Repeat 6 times.
3. Before (measured, see Evidence): 15 and 18 worker lines in two 6-round runs — `Error: No prepared statement found with ID … at closePrepared` and `RuntimeError: memory access out of bounds`. After: 0 lines.
4. Slider drag → brush the Delay histogram → slider drag again (the debt row's original gesture): histograms settle on the released range, console empty.
5. `/weekly-review?region=West` → click a Regional split bar → `Cross-filter at scale` in the sidebar mid-load → Back: console empty.
6. `bin/biac build && bin/biac preview`, repeat step 2 on the static site: console empty.

### Root cause, read in source

| Step | Where                                                                                                                                                                                                                                                                  | What it does                                                                                                                                                                        |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `src/web/src/features/crossfilter/coordinator.ts` `disconnect` and `#updateClient`; `src/web/src/features/pages/query-registry.tsx` (`control.abort()`)                                                                                                                | An unmount or an overlapping path aborts the client's `AbortController`                                                                                                             |
| 2    | `src/web/src/features/pages/run-block.ts` `runBlock`                                                                                                                                                                                                                   | `runtime.runPromiseExit(…, { signal })` interrupts the fiber                                                                                                                        |
| 3    | `src/web/src/features/data/run-query.ts` `runQuery`                                                                                                                                                                                                                    | `Effect.onInterrupt` posts `cancelSent()`, then the scope release posts `conn.close()`. `Effect.tryPromise` does **not** wait for `sendAndMaterialize`: that promise is still alive |
| 4    | `src/web/src/features/data/run-query.ts` `sendAndMaterialize`                                                                                                                                                                                                          | The live promise keeps going: `reader.readAll()` posts further `FETCH_QUERY_RESULTS`, then `finally` posts `statement.close()` — both for a connection already disconnected         |
| 5    | duckdb-wasm `lib/src/webdb.cc` `WebDB::Disconnect` (`connections_.erase(session)`) — `https://github.com/duckdb/duckdb-wasm/blob/v1.32.0/lib/src/webdb.cc`                                                                                                             | `DISCONNECT` frees the `Connection`                                                                                                                                                 |
| 6    | duckdb-wasm `lib/src/webdb_api.cc` `duckdb_web_query_fetch_results`, `duckdb_web_prepared_close` — `https://github.com/duckdb/duckdb-wasm/blob/v1.32.0/lib/src/webdb_api.cc`                                                                                           | The connection handle is a raw pointer: `reinterpret_cast<WebDB::Connection*>(connHdl)` with no liveness check, so step 4's requests run on freed memory                            |
| 7    | duckdb-wasm `packages/duckdb-wasm/src/parallel/async_connection.ts` `ResultStreamIterator.next` (`this._inFlight = this.db.fetchQueryResults(this.conn)`) — `https://github.com/duckdb/duckdb-wasm/blob/v1.32.0/packages/duckdb-wasm/src/parallel/async_connection.ts` | The reader also pre-fetches the next chunk before the consumer asks, so one more `FETCH_QUERY_RESULTS` can already be in the worker's queue                                         |
| 8    | duckdb-wasm `packages/duckdb-wasm/src/parallel/worker_dispatcher.ts` `onMessage` (`catch (e) { console.log(e); return this.failWith(request, e); }`) — `https://github.com/duckdb/duckdb-wasm/blob/v1.32.0/packages/duckdb-wasm/src/parallel/worker_dispatcher.ts`     | Why the lines are level `log`, and why nothing reaches the UI: the rejected promise belongs to a run whose result is already discarded                                              |

Also read in source, **not yet measured**: `WebDB::Connection::CancelPendingQuery` acts only when `current_pending_query_result_ != nullptr`, which only `PendingQueryStart` sets; `SendPreparedStatement` goes through `ExecutePreparedStatement` → `StreamQueryResult` and never sets it. So `cancelSent()` looks like a no-op for every parameterised query — and every cross-filter re-query is parameterised (`CREATE_PREPARED` = `SEND_PREPARED` = 225 in one gesture). See Open decisions.

The disagreement: **framework** releases the connection from the code that owns the reader, so close always follows the last fetch; **mosaic** never releases and never cancels; **ours** releases from a second owner (the Effect scope) while the first (the promise) is still reading. No reference closes a connection from outside the reader.

## Trade-offs and what we adopt

| Axis                         | Options seen (repo → approach)                                                                                       | Trade-off                                                                                                           | Our choice, and why                                                                                                                                                                              |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Who closes the connection    | framework → the reader's own `finally`; mosaic → nobody; ours today → the Effect scope, concurrently with the reader | Closing from outside is only safe once the reader has stopped                                                       | Keep one connection per query (ADR-0005, ADR-0007 concurrency per client), but make every post for a connection finish before its `DISCONNECT`: the release waits for the in-flight work to stop |
| How an abandoned query stops | mosaic → it does not, the result is dropped; framework → it does not; ours → `cancelSent()` then close               | Draining a 200,000-row stream nobody wants costs worker time; stopping early needs the reader loop to see the abort | Stop reading at the next chunk boundary, close the statement, then disconnect. Whether `cancelSent()` stays is an Open decision                                                                  |
| Order on the worker          | duckdb-wasm processes posts in arrival order                                                                         | An already-posted pre-fetch (root cause step 7) must be awaited, not abandoned                                      | Await the reader's outstanding fetch before posting `CLOSE_PREPARED`/`DISCONNECT`                                                                                                                |

## Deviations

- We do not adopt mosaic's single never-closed connection: a connection holds one `current_query_result_`, so concurrent streamed re-queries need one each.
- We keep closing the prepared statement (framework never does); it is free once ordered before the disconnect.
