# SL-051 — Page text, widget titles and SQL values read the chosen language from one translations file

Milestone: Phase 5 — Query files, translations, search · State: partial — awaits its demo · Depends on: — · Closes: GAP-048, GAP-049

> Delete this file when the slice ships. Every path below was verified on disk on 2026-10-20 (`test -e`); paths marked **new** do not exist yet. Settled with the owner on 2026-10-20: translations live in `translations.yaml` at the project root; every other choice follows the references and community convention, decided below from the evidence.

## Outcome

An author writes `translations.yaml` once with `en` and `fr` keys, writes `{$translations.revenue}` in page text, `title={$translations.revenue}` on a widget and `{{$translations.revenue}}` in SQL, and a reader picks Français from a header menu or opens `?lang=fr` and sees the page in French with `<html lang="fr">`; a key missing in `fr` shows its `en` value.

## Demo

1. Cold start: `bin/biac dev`, open `/weekly-review`. The headings and the input titles named in the Baseline read their `en` values from `translations.yaml`; `document.documentElement.lang` is `en`.
2. Open the header's language menu (beside the theme toggle): it lists English and Français by their own names, English checked. Pick Français: the same headings and titles switch to French without a reload, `<html lang>` reads `fr`, the URL gains `?lang=fr`.
3. Reload: French persists. Open `/weekly-review` in a new tab with no `?lang=`: French persists (stored choice).
4. A key present only under `en` (e.g. `methodology`) renders its English value while the page is French.
5. The `west_orders` fence in Takeaways (`where label = {{$translations.region_west}}`) returns its row in both languages: `West · 140`, then `l'Ouest · 140` (the value is bound, so the apostrophe needs no escaping).
6. Edit `translations.yaml` (change `fr.weekly_review`) and save: the open page updates without a reload.
7. Write `{$translations.revenu}` in the page and save: the page is replaced by its compile error naming `pages/weekly-review.md:<line>:<column>`, `Undefined translation key: $translations.revenu` and `did you mean $translations.revenue?`; revert it. Break `translations.yaml` (bad indentation): the error names `translations.yaml:<line>`.
8. `bin/biac build && bin/biac preview`: steps 1–4 behave the same with no server-side language logic.

## Deviations

- SQL values are bound, never spliced: evidence's `label_{{ $translations.langcode }}` (a translation naming a column) cannot work, because a bound value is never an identifier. Authors write `case {{$translations.langcode}} when 'fr' then label_fr else label_en end`. Stated in `interpolate.ts`'s module comment.
- No `.sql` accessor: binding makes it unnecessary.
- A broken `translations.yaml` fails loudly instead of yielding `{}`.
- `<html lang>` follows the language, which evidence does not do.
- Language is chosen in the browser (`?lang=`, `localStorage`), not by a server cookie, because `biac build` is a static SPA folder (ADR-0008). Recorded with bound SQL values in ADR-0020.
- The shell reads the declared languages from `virtual:biac-languages` (`src/engine/languages-module.ts`), not `virtual:biac-translations`: importing the translations module from `src/web/src/router.tsx` put the file in the entry graph, so a malformed file blanked the whole app (500 on the module) and a saved file full-reloaded instead of hot-swapping — measured by 3 failing tests in `test/e2e-browser/translations.spec.ts`. The languages module serves `[]` for a broken file and accepts its own updates, its list kept in `import.meta.hot.data`.

## Out of scope

- Translated page titles in the sidebar and breadcrumbs (front-matter `title`): front-matter is static YAML, not MDX, so `$translations` does not reach it; a later slice decides a `title` key form.
- Translated data values (labels in the data itself): authored in SQL with `{{$translations.x}}` or a `case` on `{{$translations.langcode}}`, as above.
- Right-to-left layout (`dir`).
