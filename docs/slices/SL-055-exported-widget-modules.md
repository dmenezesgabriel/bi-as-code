# SL-055 — Another app imports a built module and mounts one named widget with its data, styles isolated from the host page

Milestone: Phase 6 — Embeds · State: open · Depends on: SL-054 · Closes: GAP-056

## Outcome

An author marks one widget for export, `biac build` emits a self-contained ES module beside the SPA, and a page on another origin imports it and mounts the widget: the module boots its own DuckDB-WASM against the publishing origin's `/data/` files, runs the widget's named query, and renders inside a shadow root, so the host page's styles and the widget's styles stay apart.

## Demo

The exported widget is the dashboard's `<BarChart data="region_revenue" x="region" y="revenue" title="Revenue by region" subtitle="Sum of order amounts, US dollars" />` (`pages/orders-dashboard.md` line 45, fed by the inline `​```sql region_revenue` fence at line 37). Chosen by evidence: it exercises the fullest export path — named query, parquet data file, DuckDB-WASM runtime, ECharts, chart tokens and the card wrapper — where a `<Table>` would skip ECharts and the embed page's chart offers no advantage (chrome is irrelevant to a module export).

1. Cold start: `pnpm build:cli && bin/biac build && bin/biac preview --port 4173`.
2. In a scratch directory write `host.html`: a `<div id="widget">` and a `<script type="module">` that imports the module `biac build` wrote (the name O1 declares — expected `http://localhost:4173/widgets/revenue-by-region.js`), calls its mount with the div, and reports the mounted element count and the chart's canvas/svg presence into the page. Serve it with `python3 -m http.server 8901 --bind 127.0.0.1`.
3. Open `http://127.0.0.1:8901/host.html` — the bar chart renders the region revenue query inside the host page; the module's data requests go to `http://localhost:4173/data/…` (visible in the network tab or a fetch counter).
4. The host page's own look is unchanged: its headings and text keep the browser default styles — no Tailwind preflight leak; the widget inside the shadow root is styled.
5. Console: 0 errors, 0 warnings on the host page.
6. Reload — the same result (the build is the only state).

**The disagreement the slice must make:** framework's export is vanilla JS — a function returning a DOM node, no stylesheet, no runtime to carry. Ours is a React widget fed by DuckDB-WASM in a worker and styled by Tailwind tokens, so the export must bundle a runtime, isolate styles, and bake absolute URLs. Nothing in the references answers those three; O2–O5 decide them.

## Standards that bind the design

| Fact                                                                                                                                                                                                                                                              | Source                                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Module scripts are fetched under "JavaScript module security requirements" — a cross-origin `import` fails without CORS on the module response                                                                                                                    | https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules (fetched 2026-10-22)            |
| A worker's URL "is resolved relative to the current HTML page's location", and the worker script "must be same-origin with the associated document"; "If a cross-origin worker is required, users must load it from an intermediate same-origin worker or a blob" | https://developer.mozilla.org/en-US/docs/Web/API/Worker/Worker (fetched 2026-10-22)                   |
| Shadow DOM: "none of the code inside a shadow DOM can affect anything outside it" — styles in a shadow root neither leak out nor let page styles in; CSS custom properties inherit through the boundary unless re-declared on the shadow root                     | https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM (fetched 2026-10-22) |
| vite library mode (`build.lib`) bundles a browser-oriented library entry; dependencies not bundled must be externalized                                                                                                                                           | https://vite.dev/guide/build (fetched 2026-10-22)                                                     |
| Every file a page queries is downloadable by its viewer — the module's data fetches grant nothing new                                                                                                                                                             | [ADR-0005](../adr/0005-queries-run-client-side-in-duckdb-wasm.md)                                     |
| Data files are readable cross-origin only by origins `embed.dataOrigins` lists                                                                                                                                                                                    | [ADR-0025](../adr/0025-data-files-are-readable-cross-origin-only-by-listed-origins.md)                |
| Every UI component ships a colocated stories file — the browser-true validation surface                                                                                                                                                                           | [ADR-0006](../adr/0006-component-stories-are-the-ui-validation-surface.md)                            |

## Trade-offs and what we adopt

| Axis             | Options seen (repo → approach)                                                                                                        | Trade-off                                                                                                                                                                | Our choice, and why                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Declaration      | framework → a config list of module files; ours → nothing today                                                                       | A config list keeps pages untouched but separates the export from the widget's definition; a tag attribute keeps them together but spreads build config across pages     | O1 — settled by T2                                                                                             |
| Module unit      | framework → any module, many exports; ours → one widget per module (the backlog row)                                                  | One widget per module keeps the baked spec small and the host's import cheap; many exports per module would need a shared runtime chunk                                  | One widget per module — the backlog row's contract                                                             |
| Runtime carrying | framework → vanilla JS, npm self-hosted separately; ours → bundle React and ECharts into the module vs externalize them onto the host | All-in-one is one import and no host requirements; externals shrink the module but make the host provide React and ECharts at pinned versions                            | O3 — settled by T3                                                                                             |
| Style isolation  | framework → none needed; ours → a shadow root vs a scoped root class                                                                  | A shadow root is the platform's boundary (preflight cannot leak); a scoped root class keeps the light DOM but must prefix every rule and cannot stop preflight           | O4 — settled by T1                                                                                             |
| Data             | framework → FileAttachment, a plain fetch of a baked URL; ours → the module boots its own DuckDB-WASM vs the host supplies rows       | Self-contained means a 33 MB wasm fetch and a worker on the host page; rows-in makes the host do SL-054's work and splits the query from the widget                      | The module boots its own runtime — the backlog row says "with its data", and rows-in would only restate SL-054 |
| Module CORS      | framework → the hosting provider's job; ours → `biac dev` and `biac preview` must send it for the module path                         | Without it the cross-origin import fails (Standards); reusing `embed.dataOrigins` keeps one embedding relationship, a new key splits two grants that are one in practice | O6 — settled by T3                                                                                             |

## Deviations

| What                                                                                     | Why                                                                                                                                                              |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Not porting framework's transpile-based export (source rewriting with baked resolutions) | Ours is a vite/React build; the export is a vite library-mode build, not text transpiling — the resolutions framework bakes by rewriting, vite bakes by bundling |
| Not accepting host-supplied rows                                                         | The backlog row says "with its data"; SL-054 already lets a host fetch raw files, so a rows-in API would only restate it                                         |
| Not serving the module from `biac dev`                                                   | The export is a build artifact; the authoring loop is edit → build → preview. Dev serving is a follow-up if asked                                                |
