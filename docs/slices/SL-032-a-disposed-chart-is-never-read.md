# SL-032 — A disposed chart is never read

Milestone: Phase 1 — Known debt · State: partial · Depends on: — · Closes: the Known-debt DEF-001 row (`layerStack` after an echarts dispose)

> A PRD exists so the executing agent **never guesses and never assumes**. Every path below was checked on disk on 2026-10-14; every number carries the command or script that produced it.

## Outcome

A user who navigates away from, re-themes, or cross-filters a page while its charts are mid-paint or mid-gesture never gets `TypeError: Cannot read properties of null (reading 'layerStack')` in the console: nothing reads a chart's zrender painter after that chart is disposed.

## Demo

A numbered script a human runs from a cold start. The slice is not `shipped` until this has been run in the real app.

1. `pnpm build:cli && bin/biac dev --port 5532`, open `http://localhost:5532/weekly-review` in Chrome with DevTools → Console open and DevTools → Performance → CPU throttling at 6×.
2. Hover each chart, click a Regional split bar, toggle an Order mix legend entry, start a brush on Order size and — mouse still down — click `Cross-filter at scale` in the sidebar; release; brush Distance; browser Back. Repeat 6 times.
3. Toggle the theme twice while the page's charts are still loading. Repeat 6 times.
4. Console: no `layerStack` `TypeError` and no `[ECharts] Instance … has been disposed` warning.
5. `bin/biac build && bin/biac preview`, repeat steps 2–4 on the static site.
6. The regression the slice adds (T1) passes under `systemd-run --user --scope -p CPUQuota=50%`.

### Root cause, read in source

| Step | Where                                                                                                                                                                                                                                                                                                         | What it does                                                                                                                                                                                                  |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `node_modules/.pnpm/zrender@6.1.0/node_modules/zrender/lib/canvas/Painter.js` `_paintPerCursorInRect`                                                                                                                                                                                                         | an **incremental** layer (`isIncrementalLayer`) paints under a 15 ms budget and stops early when it runs over                                                                                                 |
| 2    | same file, `CanvasPainter.prototype._paintList` (~250–269)                                                                                                                                                                                                                                                    | an unfinished paint schedules `requestAnimationFrame(() => self._paintList(list, prevList, redrawId))`; the only bail-out is `this._redrawId !== redrawId`                                                    |
| 3    | same file, `CanvasPainter.prototype.dispose` (~687–693)                                                                                                                                                                                                                                                       | nulls `root`, `storage`, `_domRoot` and `_i` — **not** `_redrawId`, and cancels no frame                                                                                                                      |
| 4    | same file, `eachLayer` (~77–89)                                                                                                                                                                                                                                                                               | the continuation's `_doPaintList` → `eachLayer(this._i, …)` reads `null.layerStack` and throws from a `requestAnimationFrame` callback, so nothing in our code is on the stack                                |
| 5    | `node_modules/.pnpm/echarts@6.1.0/node_modules/echarts/lib/chart/heatmap/HeatmapView.js` `render` (~119) → `_renderOnGridLike(…, 0, count)` with no `useIncremental`; ~260 `getIncrementalId(seriesModel, undefined)`; `…/lib/util/model.js` `getIncrementalId` (~927–930, `retrieve2(useIncremental, true)`) | **every heatmap rect is incremental on every full render, at any row count** — the missing argument defaults to `true`; echarts `master` `src/chart/heatmap/HeatmapView.ts` (~128, ~335) is unchanged         |
| 6    | `…/lib/util/model.js` `preparePipelineContext` (~935, `dataLen >= pipeline.threshold`); `…/chart/helper/SymbolDraw.js` `incrementalUpdate` (~191–197)                                                                                                                                                         | scatter symbols are incremental only past `progressiveThreshold` (3000 rows) — no page plots that many: the largest series is `/weekly-review`'s scatter (`region_week`, 39 rows); histograms are binned bars |

So: a chart with an incremental layer — today, any heatmap — disposed in the frame between a paint that overran its budget and its continuation. A loaded host makes the overrun likely; the dispose comes from our unmount — here the `?region=Atlantis` prune swapping chart faces. No guard in our code can reach the continuation: echarts' public API is not on the path.

## Trade-offs and what we adopt

| Axis                         | Options seen (repo → approach)                                                                                                | Trade-off                                                                                                                     | Our choice, and why                                                                                                                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where the fix lives          | evidence, streamlit → `isDisposed()` guards around their **own** deferred calls; neither touches zrender's paint continuation | Guards in our code cannot reach a zrender-scheduled frame                                                                     | Out of our call sites: the fix is either in what we ask echarts to render or in zrender itself                                                                                     |
| Remove the incremental layer | echarts → `progressive: 0` per series disables progressive rendering (the line series' own default, `LineSeries.js` ~143)     | Large scatter/heatmap series paint in one frame instead of chunks; our charts plot query results, and T1 measures the largest | Rejected — `HeatmapView.render` never reads `progressive`: its rects are incremental regardless (Root cause step 5)                                                                |
| Patch zrender                | `pnpm patch` on `zrender@6.1.0` with `if (!this._i) return` in `_paintList`, plus an upstream issue                           | Fixes every chart type, but a patched dependency is ours to carry across upgrades                                             | **Adopted** — `dispose` sets `_redrawId = null`, so `_paintList`'s own `redrawId` check drops the pending frame; covers every incremental element; no upstream issue (user's call) |
| Theme flip                   | evidence → dispose + re-init; streamlit → `setTheme` in place                                                                 | Fewer disposes means fewer chances, but not zero (unmount still disposes)                                                     | Out of scope — it narrows the race, it does not close it                                                                                                                           |
