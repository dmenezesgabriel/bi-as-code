# SL-043 — Editing a data file under `biac dev` refreshes the open page

Milestone: Phase 3 — Data loaders · State: open · Depends on: SL-042 · Closes: GAP-037

## Outcome

With a page open under `biac dev`, a user who edits a `data/*.js` loader or rewrites a static `data/` file sees that page's queries, tables and charts show the new figures within a few seconds — with no manual reload and without losing the page's scroll position, filter values or URL params.

## Demo

1. Cold start: `bin/biac dev`, open `/weekly-orders` at the URL it prints. Note the first row of the table (`1 / 26 / 1,047` today) and the row count (`13 rows`). In devtools set `window.__mark = 1`.
2. Edit `data/weekly-orders.csv.js` so it emits different figures (e.g. change the week count or a multiplier) and save. Within ~3 s the table shows the new figures; `window.__mark` is still `1` (no reload); the dev log shows one loader run.
3. Break the loader (`throw new Error("boom")` at the top) and save. The page shows the located loader error inline, as SL-042 shipped it, without a reload. Revert the edit and save: the figures come back, `window.__mark` still `1`.
4. Open `/weekly-review`, set a filter value and `window.__mark = 1`. Rewrite `data/orders.parquet` with different rows (e.g. `duckdb -c "COPY (FROM 'data/orders.parquet' LIMIT 100) TO 'data/orders.parquet.new' (FORMAT parquet)" && mv data/orders.parquet.new data/orders.parquet`, after backing the original up). Within ~3 s every figure on the page reflects the new rows; the filter value and `window.__mark` survive.
5. Restore `data/orders.parquet` and the loader: the page returns to the original figures.
6. Reload: the page shows the same figures as before the reload.
7. `bin/biac build` + `bin/biac preview`: the built site carries no HMR listener and behaves as before (`import.meta.hot` is `undefined`).

## Trade-offs and what we adopt

| Axis                       | Options seen (repo → approach)                                                                            | Trade-off                                                                                                                        | Our choice, and why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 Cache-busting           | framework → new `?sha=` URL per change; (none other)                                                      | A same-URL re-read is less code but depends on duckdb-wasm not caching file metadata or bytes across re-registration             | **Settled in T2 by measurement (duckdb-wasm `1.32.0`)**: re-registering a name at the same URL is a no-op that keeps the first bytes (no new GET, stale figures); at a `?v=` URL the worker throws `File already registered`. and with the drop alone a smaller rewritten parquet fails `No magic bytes found at end of file` (DuckDB's external file cache keeps the old bytes and size by path). Adopted: `registerSource` calls `dropFile(source)` before `registerFileURL`, and `duckdb-live.ts` sets `enable_external_file_cache = false` at open — same URL, fresh read, no port change |
| D2 Push channel            | framework → its own per-page WebSocket `update` message                                                   | A second socket duplicates what Vite's HMR channel already does under `biac dev`                                                 | Vite custom HMR event `biac:data-update` `{ path: "data/<target>", version }` sent from `hotUpdate` via `this.environment.hot.send`; `hotUpdate` returns `[]` so Vite does not fall back to a full reload                                                                                                                                                                                                                                                                                                                                                                                     |
| D3 Loader source → target  | framework → `getWatchPath` watches the loader when the output does not exist                              | —                                                                                                                                | Map `data/x.csv.js` → `data/x.csv` (the existing `isDataLoaderSource` in `src/engine/data-loader.ts`); loaders re-run lazily on the client's next fetch, as framework does and as `createDataLoaderCache`'s mtime check already does                                                                                                                                                                                                                                                                                                                                                          |
| D4 Loading state on re-run | evidence → keep the old result painted (`_isRefreshing`); framework → recompute the cells                 | Keep-stale avoids a skeleton flash but needs a new refreshing path through `query-registry.tsx`                                  | **Existing `loading` reset** (user decision, 2026-10-17): re-registration resets blocks to `loading`, the same as a param change. | D5 Page scoping            | framework → server watches only the page's referenced files; streamlit → server reruns only the open page | Server-side scoping needs the server to know each open page's sources — Vite has one broadcast channel, not per-page sockets     | Broadcast every data change; each open page drops paths not among its merged `sqlTables` sources (config ∪ page). ## Deviations

- No per-page socket (framework): Vite's HMR channel carries one broadcast event and each page filters (D5). Stated in a code comment at the listener.
- No keep-stale refresh (evidence `_isRefreshing`): the existing loading state is reused (D4).
- No "Rerun" prompt (streamlit `runOnSave` off): refresh is always automatic, as in framework.

## Open decisions

- None open. D1 settled in T2: drop the file, then re-register at the same URL, with DuckDB's external file cache off (code comments in `src/web/src/features/data/register-source.ts` and `duckdb-live.ts`).

## Out of scope

- Timer-driven auto-refresh (evidence `auto_refresh`) — no data-loader need; would be its own slice.
- Non-`.js` loaders — SL-044.
- A page whose `sql:` mapping itself changes — already handled by page HMR in `hotUpdate`.
- `biac build` / `biac preview` behaviour — unchanged; `import.meta.hot` is `undefined` there.
