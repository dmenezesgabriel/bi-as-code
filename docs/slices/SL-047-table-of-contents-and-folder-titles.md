# SL-047 — A project sets whether pages show a table of contents and what it is called, and names its sidebar folders

Milestone: Phase 4 — Project and page settings, themes, layouts · State: open · Depends on: SL-046 · Closes: GAP-040, GAP-041

## Outcome

An author sets `layout: { table_of_contents: false, table_of_contents_label: "Contents" }` in `biac.config.ts`, or either key in one page's front-matter (the page wins), and every page's right-rail table of contents follows it; `directories: { "pages/nested": { title: "Planning" } }` renames that sidebar folder and its breadcrumb. Today the rail can only be hidden page by page, its heading is always "On this page", and a folder is always named `deslugify(<folder>)`.

## Demo

1. Cold start: `bin/biac dev` at 1440px. On `/nested/page` the sidebar folder and the breadcrumb read `Nested`. On `/weekly-review` the ToC rail shows 7 links under the heading `On this page`, which is also its `nav[aria-label]`. A page with fewer than two headings (`/nested/page`, `/`) has no rail at all, since `src/web/src/features/chrome/nav-toc.tsx` returns null below 2 headings.
2. Add `directories: { "pages/nested": { title: "Planning" } }` to `biac.config.ts` and save. The tab reloads by itself; sidebar folder and breadcrumb read `Planning`; the URL is still `/nested/page`.
3. Add `layout: { table_of_contents_label: "Contents" }`. The `/weekly-review` and `/regional-orders` rail heading and `nav[aria-label]` read `Contents`.
4. Add `table_of_contents: false` to `layout`. Neither `/weekly-review` nor `/regional-orders` shows the rail; the example page (added in T4), whose front-matter sets `table_of_contents: true`, keeps its rail.
5. Type `"pages/nestd"` under `directories`: a located error at `biac.config.ts:<line>:<column>` names the key, the accepted folders (`"pages/nested"`) and the closest. Type `table_of_contents: "no"` in a page's front-matter: the page shows the located front-matter error naming `table_of_contents`, `a boolean` and `"no"`. Fix both — the page comes back by itself.
6. `bin/biac build` + `bin/biac preview`: the same labels, folder title and rails render.
7. Reload — the effect persists.

## Deviations

- A `directories` key must name a first-level folder under `pages/` that holds a page (`"pages/<folder>"`); a deeper key (`"pages/a/b"`) is an error, not ignored — our sidebar has two levels (`src/engine/nav-tree.ts`), so a deeper title would silently do nothing. Stated in a code comment at the check.
- The ToC `nav` keeps an `aria-label`, equal to the label — framework's has none.

## Open decisions

- **O1 — label key shape.** Settled: flat `table_of_contents_label` beside `table_of_contents` — matches the flat `layout` keys, one validator per key; framework's nested `table_of_contents: { show, label }` rejected.
- **O2 — empty label.** Settled: an empty or blank `table_of_contents_label` is a located error (`expected a non-empty string`) in front-matter and config — it would leave the `nav` landmark unnamed and the rail without a heading.
- **O3 — where a stale `directories` key fails.** The check needs both the config and `discoverPages`, so it belongs where the manifest is built (`src/engine/pages-plugin.ts` `load` for `RESOLVED_MANIFEST_ID`), not in `loadBiacConfig`. Decide how it is located (`src/engine/config-key-position.ts` on the `directories` key path) and that it fails `biac build` like every other config error.
