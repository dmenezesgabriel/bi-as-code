# SL-015 — Cross-filter stays responsive while I drag a slider or brush on a large dataset

Milestone: Phase 1 · State: open · Depends on: SL-013, SL-014 · Evidence: `docs/research/interaction-reference.md` (R2) · Closes: —

> Written per `docs/slices/_TEMPLATE.md`. Every `research_repos/` path below was verified with `test -e` in the session that wrote this file (2026-10-09). Line ranges rot — paths are the citation; open the file.

## Outcome

On a page with ~200k rows, dragging a slider or brushing a histogram re-queries each cross-filtered chart a bounded number of times per drag, never paints a result older than one already painted, and settles on the clause the user released.

## Demo

1. Cold start: `bin/biac dev`, open `http://localhost:<port>/crossfilter-scale` (page added by T1).
2. Drag the slider end to end over ~2 s — every histogram repaints progressively during the drag (not only after release), and the browser stays responsive (no frozen frames).
3. Release — every histogram shows the counts for the released extent: the slider is its own source, so all three histograms' bars sum to the same total (hover a bar for its count; `crossfilter-scale.spec.ts` asserts the equal totals).
4. Brush an interval on one histogram and drag it — the other histograms follow; the brushed histogram itself is not re-queried (cross-filter skip, SL-013/SL-014).
5. `console` stays clean (named known debt only).
6. Regression: `/weekly-review` — Region dropdown ↔ Amount slider and the Order size histogram brush still cross-filter as shipped in SL-013/SL-014.

**Before:** see "Baseline" below — 355 rows on `/weekly-review`, and 200k rows on `/crossfilter-scale` (T1).

## Trade-offs and what we adopt

| Axis | Options seen (repo → approach)                        | Trade-off                                                                                                                                                                                                                                             | Our choice, and why                                                                                                                                                                                                                                                                                                                                                                            |
| ---- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1   | finish + latest-wins (mosaic) vs abort (evidence, us) | Abort keeps the worker free but, when one query outlasts the publish interval, every query is cancelled before it paints — the chart freezes until the drag stops. Latest-wins paints every completed query but may run one stale query to completion | **Latest-wins (mosaic)**, settled by T1, shipped in T2 (`src/web/src/features/crossfilter/async-dispatch.ts`): abort painted **0** frames per chart (39–59 of 60 queries per chart cancelled); latest-wins cancels **0** and issues 20–25 per chart. The per-client abort stays only for cross-path overlap (connect/`requestQuery`/a second selection) and disconnect. Record in the ADR (T3) |
| D2   | rAF vs fixed ms vs release                            | Release (streamlit) gives no live feedback during a drag — the opposite of the cross-filter UX mosaic exists for; 500 ms (evidence) adds fixed lag to every interaction; rAF adds ≤ 1 frame                                                           | **No clock on the selection path** (decided 2026-10-09): mosaic's rAF debounce sits only on the per-client `requestUpdate` path, never on selection dispatch, and an idle dispatch must stay synchronous (URL-seeded first paint, every sync-publish test); the queue filter already collapses a burst. Brush keeps its echarts 150 ms throttle; text input keeps its 300 ms commit            |
| D3   | per selection vs per client                           | Per selection keeps a group's charts in step (all settle before the next clause); per client lets a fast chart run ahead of a slow one                                                                                                                | **Per selection** (T2): `Coordinator` returns the group's `Promise.allSettled` from its subscription, so a selection holds its next delivery until every client in the group settles                                                                                                                                                                                                           |
| D4   | same-source drop (mosaic) vs drop all                 | Drop-all loses a different widget's clause that queued behind a drag                                                                                                                                                                                  | **Same-source drop under cross, drop-all otherwise** (mosaic `queueFilter`), shipped in T2: `Selection.#emit`; readers resolve against the delivered snapshot, not the queued one (mosaic `willEmit`)                                                                                                                                                                                          |
| D5   | committed parquet vs generated file                   | A committed 200k-row parquet costs MBs in history forever; a generator script needs a run step before `bin/biac dev`                                                                                                                                  | **Committed**, settled by T1: `data/flights.parquet` zstd is 822,297 bytes (< 2 MB), byte-identical across regens (`src/web/scripts/generate-data.mjs`); `copyShippedProject` copies `data/` into every e2e server, so a gitignored file would be missing on a fresh clone                                                                                                                     |
| D6   | keep painted (mosaic) vs loading face (evidence, us)  | The loading face tells the reader the numbers are stale but blanks every chart on every publish — with any throttle the drag still shows skeletons; keeping the last render shows live motion but stale counts for one query                          | **Loading face kept** (decided 2026-10-09). Measured with latest-wins: paints during a slider drag rose from 0/0/0 to 3–7 (delay), 1–2 (distance), 0 (time — the last query of each round batches its success with the next `loading` into one render). A keep-last-rows trial was no better under the same load (2 s queries, a failed run)                                                   |

## Baseline

`bin/biac dev` → `/weekly-review` (355 rows), headless `playwright-cli`, 2026-10-09. Method: patch `Worker.prototype.postMessage` in the page to log every duckdb-wasm request `type` with `performance.now()`, then drag the Amount slider's Maximum thumb with 7 `mousemove` steps (`mousedown` → 7 moves → `mouseup`). T1 reuses this method on the large page.

| Measure                                                  | Value                                                                                                                                                                                                                 |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Slider value change                                      | 38–44 → 38–43 (`?amount=38+-+43`) — the drag died after its first step: every URL change re-ran every fence, the slider's bounds source went `loading` and disabled it (fixed by T0; the same drag now reaches 38–39) |
| Worker requests during the drag                          | `CONNECT` 14, `DISCONNECT` 14, `CREATE_PREPARED` 6, `SEND_PREPARED` 6, `START_PENDING_QUERY` 5, `FETCH_QUERY_RESULTS` 22, `CLOSE_PREPARED` 6                                                                          |
| Cancelled queries                                        | 0 (no cancel request type logged)                                                                                                                                                                                     |
| Connection lifetime per query (`CONNECT` → `DISCONNECT`) | median 113 ms, max 225 ms over 14 queries                                                                                                                                                                             |
| Console                                                  | 0 errors, 0 warnings (React DevTools info only)                                                                                                                                                                       |

Reading: even at 355 rows a cross-filter query holds its connection ~113 ms — about 7 animation frames and close to the brush's 150 ms dispatch throttle. A slider drag that publishes faster than that is where D1 (abort vs latest-wins) starts to matter; T1 measures how that scales at 200k rows.

### 200k rows — `/crossfilter-scale` (T1)

`test/e2e-browser/crossfilter-scale.spec.ts`, 2026-10-09, four runs under `scripts/run-capped.sh` (Chrome new headless — see the spec's `test.use` comment). Method: `test/e2e-browser/crossfilter-probe.ts` logs `CREATE_PREPARED`/`START_PENDING_QUERY`/`CANCEL_PENDING_QUERY`/`DISCONNECT` per connection (a query's lifetime; charts told apart by each fence's leading `-- <column> histogram` comment), every `data-echarts-ready` set (one finished chart mount) and every `history.replaceState` (one publish). Slider: 60 `mouse.move` steps from the Maximum thumb towards ~30% of the track, one every two animation frames. Brush: 30 steps (same pacing) across the delay histogram's first 12 bins.

| ------------------------------------ | ---------------------- | --------------------------------------------- |
| Drag duration                        | 7.2–10.3 s             | 3.4–5.6 s                                     |
| Publishes (URL writes)               | 60                     | — (session state, no URL)                     |
| Queries issued                       | 60                     | delay 0 (cross-filter skip); distance/time 11 |
| Completed / cancelled                | 1–21 / 39–59           | 2–11 / 0–9                                    |
| Query duration median (max)          | 78–113 ms (160–178 ms) | 54–283 ms (157–328 ms)                        |
| Painted updates during the drag      | **0**                  | distance/time 0–8                             |
| Release → settled (last paint)       | 407–904 ms             | 0–504 ms                                      |

Reading: under abort, a slider drag over 200k rows shows only loading faces until release — D1 settles on latest-wins, and D6 (loading face per publish) must be decided with it, or latest-wins still paints nothing. ### After T2 — latest-wins

Same spec and method, 2026-10-09. Four isolated runs plus one inside `pnpm gate`, on a shared host at load average ~20–25. A/B against HEAD (abort) in the same hour: slider drag 9.4 s, 60 issued / 59 cancelled, 0 paints, median query 147 ms.

| ------------------------------------ | ------------------------------- | ----------------------------------------------- |
| Drag duration                        | 23.7–33.1 s                     | 6.0–12.8 s                                      |
| Publishes (URL writes)               | 60                              | — (session state, no URL)                       |
| Queries issued                       | 20–25                           | delay 0 (cross-filter skip); distance/time 9–11 |
| Completed / cancelled                | all / **0**                     | all / **0**                                     |

Reading: latest-wins removes the cancels and paints during a drag, but the drag itself runs ~2.6× longer than under abort at the same load — the test paces one move per two animation frames, so frames got longer: painting completed results costs main-thread time abort never spent. The demo's "browser stays responsive" step does not hold yet; T3's ADR weighs per-paint cost and a frame clock against it. The "time" chart never paints mid-drag (D6 row). `test/e2e-browser/crossfilter-probe.ts` `waitForSettled` now re-checks a macrotask later: under `pnpm gate` load a queued delivery's first worker request landed after a > 750 ms stall and read as settled.

## Deviations

- Consolidation, result cache and preaggregation are not ported (ADR-0004). T3's ADR states the measured reason.
- `cancelSent` on a superseded query is ours, not mosaic's; whether it survives D1 is stated at the point it applies in `coordinator.ts`.

## Open decisions

- Main-thread cost of painting every completed re-query during a drag (see "After T2") — T3's ADR decides whether a frame clock or cheaper repaints follow.
- Result polling: a `playwright-cli` slider drag on `/crossfilter-scale` (2026-10-09, 30 moves) sent 30 queries but 2,970 `FETCH_QUERY_RESULTS` worker requests (~99 per query; brush: 18 queries, 1,782) — a main-thread cost candidate next to painting; `src/web/src/features/data/run-query.ts` owns the polling loop. T3 measures it before deciding.
