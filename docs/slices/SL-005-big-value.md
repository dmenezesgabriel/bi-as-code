# SL-005 — `<BigValue>`/`<Value>`: fmt, delta, sparkline

Milestone: Phase 1 — A usable BI-as-code product · State: open · Depends on: SL-004 · Closes: —

## Outcome

A page author writes `<BigValue data="kpi" column="revenue" title="Revenue" fmt="usd" delta="wow_pct" deltaFmt="pct1" text="vs. prior week" sparkline="weekly_revenue" />` and gets a KPI headline — small title, formatted scalar, signed delta indicator with direction arrow and color, inline sparkline — while `<Value data="orders" column="revenue" fmt="usd0" />` renders a formatted scalar inline in prose. Standalone `<Delta>` and `<Sparkline>` tags ship too: the presentational pieces exist for `<BigValue>` regardless, and evidence ships both as tags. Every tag binds named ` ```sql ` fence results through the registry — no tag issues its own query.

## Demo

1. Cold start: `pnpm install && pnpm build:cli`, then `bin/biac dev` from the repo root, open `http://localhost:5175/weekly-review`.
2. A KPI row under "Overview" shows `<BigValue data="kpi" column="revenue" title="Quarter revenue" fmt="usd" delta="wow_pct" deltaFmt="pct1" text="last week vs. prior" sparkline="weekly_revenue" />`: title line, `$<auto-scaled>` value, a `▲ +x.x%` delta in green, and a 13-point sparkline to its right.
3. The prose sentence "Quarter revenue closed at <Value data="kpi" column="revenue" fmt="usd" />, up <Delta data="kpi" column="wow_pct" fmt="pct1" text="WoW" /> on the prior week." renders both scalars inline — the delta carrying its arrow.
4. `<Sparkline data="weekly_revenue" />` renders the same series standalone; `<Sparkline data="weekly_revenue" type="bar" />` renders bars.
5. Open `http://localhost:5175/weekly-review?region=Atlantis` — the KPI shows `–` for the value and hides the delta and sparkline (empty result is not an error).
6. Point one `<BigValue>`'s `data` at an undeclared name — it shows an inline `role=alert` naming the unknown query; the rest of the page renders. Point `column` at a name absent from the row — the alert names the column and lists the available ones. Revert both.
7. Set `fmt="bogus"` on one widget — inline alert names the unsupported format code. Revert.
8. `console` stays clean throughout; no network re-query fires on any render (the registry already holds the rows).

## Deviations

- **`column=` names a result column, not SQL** — evidence's `value="sum(total_sales)"` is a SQL expression; ours binds a named fence's materialized row, so `column="revenue"` (first key when omitted). A comment at the prop's type says the SQL lives in the fence.
- **No `comparison={}` / `date_range` / benchmark / target SQL generation** — evidence's comparison is a 1372-line SQL generator requiring `date_range` semantics we don't implement; the author expresses comparisons as columns in the fence. Revisit only if SL-013's coordinator makes widget-generated SQL cheap.
- **No `metric=`** — evidence's metric catalog (`metrics/resolve-metric`) has no counterpart here; there is no semantic layer to reference.
- **Hand-rolled SVG sparkline, not echarts** — echarts enters with SL-006's wrapper (dep-cruiser wrap site `features/widgets/charts/`); when it lands, the sparkline display may delegate. Our sparkline has no hover tooltips, `fit_to_data`, or `connect_group` in v1.
- **`Intl`-based presets, not ssf** — raw Excel-style codes are unsupported (`ssf` is unmaintained since 2022-06); unknown codes error rather than pass through. Date-part numeric tricks (`ddd` 1–7 → day name, `mmm` 1–12 → month, `yyyy`, `h`, `quarter`/`qq`) are not ported — our authors produce `Date`/string cells directly in SQL.
- **No `filters=`, `where=`, `having=`, `order=`, `limit=` widget props** — filtering is authored in the fence (`{{params}}`/`{{query}}`); `filters=[…]` consumption is SL-009.
- **No `link`, `info`/`info_link`, `text_size`, `max_width`/`min_width`, `class_name`/`value_class`/`title_class` chrome props** — v1 keeps `title`, `fmt`, `column`, `row`, delta and sparkline props, plus `color`/`redNegatives` on `<Value>` (evidence parity, ~5 lines each).
- **No count-up tween** — evidence animates the value via `Tween` honoring `prefersReducedMotion`; polish, not capability. Revisit in a later pass.
- **No standalone Vega-Lite/proto layer** — streamlit's chart spec machinery is not a model we adopt; our sparkline is one component.
- **`delta` shows the column's own value** — evidence's `comparison.display_type` (pct/abs/compared_value) is unneeded because the author chooses the delta's unit in SQL; `deltaFmt` formats it, `text` captions it.

## Open decisions

- **Sparkline y-domain** — evidence anchors at the data min only with `fit_to_data`; streamlit's area baseline uses `min(0, dataMin)` (`Metric.tsx` ~L64–109). Settle in T2 by reading both: default 0-baseline unless the series is all-positive-and-far-from-zero is likely wrong for KPI sparklines (a 0-anchored y flattens real movement); the call the code makes must be a unit-tested constant, not a vibe.
- **Neutral range defaults** — evidence `neutral_range` defaults `[0,0]` (exactly 0 is neutral; everything else signs). For a WoW delta, ±small values reading as "up/down" may mislead; settle the default and the prop's shape (`[min,max]` with `null`=∞, evidence's) in T2 with tests.
- **Sparkline `type` prop name** — `sparklineType` vs `type` on `<BigValue>` (flat props can't reuse bare `type` safely if a later prop wants it); settle at PRD implementation time — lean `sparklineType`/`sparklineColor` namespaced, bare `type`/`x`/`y`/`color` on standalone `<Sparkline>`.
