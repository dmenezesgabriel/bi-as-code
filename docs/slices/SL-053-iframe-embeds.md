# SL-053 — A page shows inside another site's iframe, without chrome, framed only by the origins the project allows, at the height of its content

Milestone: Phase 6 — Embeds · State: partial — awaits its demo · Depends on: — · Closes: GAP-052, GAP-053, GAP-054

## Outcome

An author marks a page `sidebar: false` and `header: false`, lists the sites allowed to frame it in `biac.config.ts`, and another site on one of those origins shows the page in an `<iframe>` that grows to the page's height — while every other origin is refused by the browser.

## Demo

1. Cold start: `pnpm build:cli && bin/biac dev`. In a scratch directory, write `host.html` holding `<iframe id="f" src="http://localhost:5175/<embed page>" width="800" scrolling="no"></iframe>` and a `message` listener that sets `f.height` from the page's message after checking `event.origin === "http://localhost:5175"`. Serve it with `python3 -m http.server 8901 --bind 127.0.0.1`.
2. Open `http://localhost:5175/<embed page>` directly — no sidebar, no header, no ToC rail; only the page's content.
3. Without `embed.origins` in `biac.config.ts`, open `http://localhost:8901/host.html` — the frame is refused (the browser shows its blocked-frame placeholder) and `curl -s -D - -o /dev/null http://localhost:5175/<embed page>` shows `Content-Security-Policy: frame-ancestors …` without `http://localhost:8901`.
4. Add `embed: { origins: ["http://localhost:8901"] }` to `biac.config.ts`, restart — the frame shows the page and its height matches the page's content (no inner scrollbar); resize the host window narrower and the frame grows taller.
5. Open the same host page as `http://127.0.0.1:8901/host.html` — a different origin, not on the list: the frame is refused again.
6. Repeat 3–5 on `bin/biac build && bin/biac preview` — same headers, same results.
7. `embed: { origins: ["https://example.com/path"] }` (a path) or `["*"]` fails `biac dev` with a located error naming the key, the value and the expected shape.

## Standards that bind the design

| Fact                                                                                                                                         | Source                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `frame-ancestors` takes `'none'`, `'self'`, host and scheme sources and is not honoured in a `<meta>` element — it must be a response header | https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors |
| `frame-ancestors` obsoletes `X-Frame-Options` in supporting browsers; OWASP's default is `X-Frame-Options: DENY`                             | https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html                                |
| Always give `postMessage` an exact `targetOrigin`, never `"*"`, and verify `event.origin` on receipt                                         | https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage                                         |
| A static build is one SPA folder, so a header cannot ship inside it — whoever serves it sends the header                                     | `docs/adr/0008-static-build-is-a-spa-folder.md`                                                             |

## Trade-offs and what we adopt

| Axis                    | Options seen (repo → approach)                                                                    | Trade-off                                                                                                                                       | Our choice, and why                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Where chrome is dropped | framework → front-matter per page; streamlit → `?embed=true` per URL                              | Front-matter is reviewable and matches our layout keys; a query parameter lets any page be embedded but makes chrome a reader-controlled switch | Front-matter, beside `table_of_contents` (`src/engine/page-layout-frontmatter.ts`); a query parameter is O1                     |
| Which chrome            | framework → `sidebar`, `header`, `footer`, `pager` independently; our `nav.sidebar` → all at once | Independent switches cover "header but no sidebar"; we have no footer or pager                                                                  | `sidebar` and `header`, independent, as framework (O1 settles what the header's sidebar toggle does when only `sidebar: false`) |
| Framing policy          | evidence → `DENY`; framework, streamlit → none                                                    | None lets any site frame any page (clickjacking); `DENY` forbids the capability                                                                 | Deny by default, allow listed origins with `Content-Security-Policy: frame-ancestors` (O2: `'none'` or `'self'` as the base)    |
| Height                  | framework → `{height}` to `"*"`; streamlit → iFrameResizer protocol                               | `"*"` leaks the page's height to any framer; a third-party protocol is a dependency for one number                                              | Our own message, posted only to the listed parent origin (O3, O4); no dependency                                                |

| O1  | Are `sidebar` and `header` independent per page (framework) or one switch (`nav.sidebar`, streamlit `?embed`)? With `sidebar: false` and a header, does the header lose its sidebar toggle? Front-matter only, or also a query parameter?      | **Settled (T1):** independent strict booleans, and each one a page sets wins over `nav.sidebar` key by key, so `sidebar: true` brings a sidebar back under `nav.sidebar: false` — framework `framework/src/render.ts` `sidebar = options.sidebar`, and our own layout merge (`src/web/src/features/pages/page-router.tsx` `CompiledPage`). The toggle belongs to the sidebar, as framework renders it inside `renderSidebar`: `sidebar: false` drops it from the header, and `header: false` keeps it as a floating button so the drawer below `lg` stays reachable. Front-matter only: a query parameter would make chrome a reader-controlled switch. | O2  | Base of `frame-ancestors`: `'none'` (OWASP, evidence `DENY`) or `'self'` (lets a page frame its own site, framework's example). Also send `X-Frame-Options` for browsers without CSP 2?                                                        | **Settled (T2), [ADR-0022](../adr/0022-framing-is-denied-unless-the-project-lists-the-origin.md):** `frame-ancestors 'none'` when no origin is listed, otherwise exactly the listed origins with no `'self'` (CSP3 `ancestor-source-list`: `'none'` stands alone); `X-Frame-Options: DENY` always rides along. The earlier claim that sending both would deny the listed origins was wrong: the HTML Standard ignores `X-Frame-Options` whenever `frame-ancestors` is present (https://html.spec.whatwg.org/#the-x-frame-options-header), so it only makes browsers without CSP 2 fail closed. Origins are validated as `new URL(o).origin === o`, http(s), CSP `host-char` hosts (`src/engine/embed-config.ts`); `biac dev` reads them per request (`src/engine/frame-ancestors.ts` `frameAncestorsMiddleware`, first in `src/engine/pages-plugin.ts`), `biac preview` once at start. A browser test must serve its host page from a real loopback origin: Chromium's Local Network Access checks block a `page.route`-fulfilled public-looking host from framing localhost before the CSP is consulted                  |
| O3  | How the framed page learns its parent's origin for an exact `targetOrigin`: `location.ancestorOrigins` (not in Firefox), `document.referrer` checked against the allowlist, a handshake message from the parent, or one post per listed origin | **Settled (T3), [ADR-0023](../adr/0023-a-framed-page-reports-its-height-only-to-a-listed-parent.md):** `location.ancestorOrigins[0]`, falling back to the origin of `document.referrer`, posted only when `embed.origins` lists it (`src/web/src/features/chrome/frame-height.ts` `parentOrigin`). Measured 2026-10-21 with `playwright-cli` (host `http://localhost:8901` framing `http://localhost:8902`): Chromium 152 and Firefox 156 both expose `ancestorOrigins[0] === "http://localhost:8901"` and `referrer === "http://localhost:8901/"` — the "not in Firefox" premise is out of date (MDN: Baseline since February 2026); under `referrerpolicy="no-referrer"` the referrer is `""` in both and Firefox masks `ancestorOrigins[0]` as `"null"`, which is never listed, so that host gets no height (fail closed). A handshake costs every host code, and one post per listed origin sends wasted messages every load; `embed.origins` now reaches the browser through `virtual:biac-config` (`src/engine/config-module.ts`)                                                                                   |
| O4  | Message shape and measured element: framework `{height}` of `document.documentElement` vs a namespaced `{type, height}`; and when to post (every resize, debounced)                                                                            | **Settled (T3), ADR-0023:** `{ type: "biac:height", height }` so a host filters on `type` as well as `event.origin`; `height` is the `scrollHeight` of `AppShell`'s content wrapper (`src/web/src/App.tsx`), observed with a `ResizeObserver` and re-sent only when it changes (no debounce: RO delivers once per frame). `document.documentElement` was rejected: inside a frame `min-h-screen` is the frame's own height (measured: `min-height: 496px` in a 496 px frame), so the page could grow but never shrink — while framed the wrapper drops `min-h-screen`. Measured: the frame shrinks from its initial 600 px to 496 px at a 1280 px host, grows to 544 px at 390 px, and returns to 496 px                                                                                                                                                                                                                                                                                                                                                                                                                  |
| O5  | Does a chrome-less page still appear in the sidebar nav and site search?                                                                                                                                                                       | **Settled (T1):** yes — chrome is how a page renders, not whether it is listed. framework lists pages from config whatever their `sidebar`, streamlit `?embed` leaves its page list alone, and `index: false` already keeps a page out of search. `pages/embed-weekly-revenue.md` is in both                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
