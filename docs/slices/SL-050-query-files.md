# SL-050 — A query kept in its own `.sql` file, used by any page

Milestone: Phase 5 — Query files, translations, search · State: open · Depends on: — · Closes: GAP-046, GAP-047

> Delete this file when the slice ships. Every path below was verified on disk on 2026-10-19 (`test -e`). Settled with the owner on 2026-10-19: a page names a query file by its root path, `/queries/<path>`; there is no page-relative form.

## Outcome

An author writes a query once in `queries/region_orders.sql`, points any widget at it with `data="/queries/region_orders"` or builds on it in a fence with `{{/queries/region_orders}}`, and a typo in that path fails the page at the line that wrote it.

## Demo

1. Cold start: `bin/biac dev`, open `/weekly-review`. The "Revenue by region" bar chart reads `data="/queries/region_orders"`; the page's own `orders` fence is gone from `pages/weekly-review.md`.
2. Same page: the `region_share` fence reads `from {{/queries/region_orders}}` and its echoed result shows the same shares as before (Baseline below).
3. Open `/` (`pages/index.md`): its `orders` fence reads `from {{/queries/region_orders}}` plus its own `{{params.region}}` clause; the table and bar chart match the Baseline.
4. Edit `queries/region_orders.sql` in a text editor (e.g. add `where region <> 'West'`) and save: both open pages update without a reload; revert it.
5. Change the chart's reference to `/queries/region_order` and save the page: the page is replaced by its compile error naming `pages/weekly-review.md:<line>:<column>`, the missing `queries/region_order.sql`, and `did you mean /queries/region_orders?`.
6. Break the file's SQL (`selec region`) and save: the widgets that read it show their error state with a message that starts `queries/region_orders.sql:`; revert it.
7. Add `queries/unused.sql` containing `select 'never-shipped'`, run `bin/biac build`, then `grep -rl never-shipped build/` prints nothing and `grep -rl "sum(amount) as revenue" build/` finds the page chunks that reference the file; `bin/biac preview` shows steps 1–3 the same.

| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| How a page names a file | evidence → `/queries/x` from the root or `x` relative to the page; ours today → bare `{{name}}` for fences (`interpolate.ts`) | Bare names are shorter but share one namespace with fence names; a path cannot collide and greps back to its file       | Root path only: `data="/queries/<path>"` and `{{/queries/<path>}}` (owner, 2026-10-19). | Where files live        | evidence → `pages/` and `queries/`                                                                                            | Files under `pages/` blur pages and queries; `discover-pages.ts` would have to skip them                                | `queries/` at the project root only, subdirectories allowed (`/queries/sales/totals` → `queries/sales/totals.sql`); `resolveContained` in `src/engine/contained-path.ts` keeps `..` from escaping it                                                                               |
| Params inside a file    | evidence → none ("Variable interpolation: Not supported")                                                                     | Without params a file cannot follow a page's filter; evidence avoids it because it splices values as text               | Allow `{{params.x}}` and nested `{{/queries/…}}` in a file — `interpolateQuery` binds params as `?` args, so a file adds no injection risk, and its cycle guard (`active`) already covers nesting. | Missing file            | evidence → falls through to inline queries, then a runtime error                                                              | A runtime miss shows only when someone opens the widget                                                                 | Compile error via `file.fail(message, position)` at the `data` attribute or the fence, naming the expected `queries/<path>.sql` and `didYouMean` from `src/engine/closest-key.ts` over the files that exist                                                                        |
| Broken file             | evidence → the warehouse's parse error                                                                                        | A raw DuckDB message does not say which file                                                                            | The widget's existing error state (`QueryResult` `status: "error"`) with the message prefixed `queries/<path>.sql:`                                                                                                                                                                |

## Deviations

- `{{params.x}}` and nested file references inside a `.sql` file, which evidence forbids. Stated in a comment beside the file-expansion code: params bind through `?` placeholders.
- No page-relative references; evidence keeps them for legacy projects only.
- Only referenced files ship, where evidence ships every file. Consistent with ADR-0017; no new ADR unless T1 finds a reason.

## Open decisions

| Id  | Decision                                                 | Evidence to gather                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| O1  | `fileQueries` export vs an optional `file` on `SqlBlock` | Settled at T1: neither — a file joins `sqlBlocks` as `{ name: "/queries/<path>", sql }`. Every web consumer reads blocks by name (`interpolateBlocks`, `useFilteredQueryClient`), so no web file changed; fences render from hast `meta`, so a file block never renders. T3 derives `queries/<path>.sql` from the name                                                                                                                                                                                                                                                                                                  |
| O2  | How `compilePage` reads files                            | Settled at T1: the `QueryFiles` port (`read`, `list`) in `src/engine/types.ts`, injected as `compilePage`'s last parameter (default `NO_QUERY_FILES`); `diskQueryFiles` in `src/engine/disk-query-files.ts` is the adapter; `remarkQueryFiles` in `src/engine/query-files.ts` is an async transformer, which `compile` awaits                                                                                                                                                                                                                                                                                           |
| O3  | Prefixing a broken file's DuckDB error                   | Settled at T3: only a block named `/queries/<path>` is prefixed (`attributedToQueryFile` in `src/web/src/features/pages/query-file-source.ts`, applied in `runBlock`, so the registry and the filtered re-query share it). A fence that nests the file keeps DuckDB's message: measured on duckdb-wasm 1.32.0 in node, a broken nested file (`Parser Error … LINE 1: select * from (selec region, …`) and a broken clause in the fence (`Binder Error … LINE 3: group by region) where bogus = 1`) both report only a position in the combined SQL, so a prefix would guess; the `LINE` excerpt already quotes the file |

## Tasks

- [x] T1 — `data="/queries/<path>"`: the engine finds the reference, reads `queries/<path>.sql`, emits it in the page module; the registry runs it and the widget renders. A missing file is a located compile error with a suggestion. `biac build` ships no unreferenced file. Example: `queries/region_orders.sql` drives the `/weekly-review` "Revenue by region" chart. Measure: Baseline rows before, the same rows after, the compile error's `file:line:column` on screen, `grep -rl` over `build/`.
- [x] T2 — `{{/queries/<path>}}` in a fence builds on a file query; `{{params.x}}` and nested file references work inside a file; a cycle is an error. Example: `region_share` on `/weekly-review` and `orders` on `/`. Measure: `region_share` echoed rows and `/` table rows with and without `?region=West` against the Baseline.
- [x] T3 — a saved edit to a `.sql` file hot-updates every open page that reads it (dev); a broken file shows the widget error state prefixed `queries/<path>.sql:`. Measure: no full reload (a `window` marker survives the edit), the error text via `eval`, `console` clean after the revert.

Each task: unit, integration, e2e and e2e-browser tests, and a `playwright-cli` pass on the pages it changes (`prompt-execution.md` §5).

## Out of scope

- Page-relative references (`data="x"` resolving beside the page) — not planned.
- Editing a `.sql` file from the in-app editor — `docs/adr/0010-page-authoring-is-dev-server-only.md` covers pages only; no slice owns it.
- Translation accessors inside SQL — SL-051.
- Front-matter or filter tokens inside SQL beyond `{{params.x}}` — not planned.
